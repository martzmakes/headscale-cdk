# Build notes (raw material for a martzmakes.com post)

Running log of decisions, surprises and numbers while building this. Newest findings
get appended at the bottom of each section. Not polished; that's the post's job.

## The pitch

- Self-hosted Tailscale control plane for a home lab for about **$7/month**: one
  Lightsail box running Headscale (coordination server) + Headplane (admin UI) + Caddy (TLS),
  with Cognito as the identity provider, all as a single CDK stack.
- Why not tailscale.com? Its free plan is generous. The real reasons: owning the
  coordination server, unlimited users and devices, and learning how the pieces fit.
  Be honest in the post that tailscale.com is the easier choice for most people.

## Version archaeology (checked 2026-11-22)

- Headscale **v0.29.7** (2026-10-30). Docker Hub tags have **no `v`**: `headscale/headscale:0.29.7`.
- Headplane jumped **0.6 -> 0.7 -> 0.8.2** (2026-10-22). Things that moved:
  - `oidc.headscale_api_key` is **deprecated** -> `headscale.api_key` / `headscale.api_key_path`.
  - `oidc.redirect_uri` is **deprecated** -> derived from `server.base_url` (no `/admin` suffix).
    The deprecation message still says "will be removed in 0.7.0", yet it's still accepted in 0.8.2.
  - `server.base_url` is effectively required for SSO since 0.8.1 (SSO switches itself off without it).
  - `headscale.config_strict` is declared in the 0.8.2 schema but **never read** in the code.
  - 0.8.1 fixed "Bad Request" on actions behind a TLS-terminating proxy. That's exactly
    this setup, so don't run 0.8.0.
- Lesson for the post: blog posts and READMEs about Headplane go stale within months.
  Read `config.example.yaml` **at the tag you deploy**, and the config schema source
  (`app/server/config/config-schema.ts`) when keys look off.

## Design decisions

### Getting the Cognito client secret onto a box with no IAM role
Lightsail instances can't have an instance profile. Options considered:
1. **Embed in user data.** Simple, but the secret ends up in CloudFormation-resolved
   properties, instance metadata (readable by any process on the box via IMDS) and
   cloud-init logs. And CFN `UserData` is **replace-on-update**, so a rotation means a new instance.
2. **SSM SecureString + a scoped IAM user.** You still have to get a long-lived access
   key onto the box, which is a *worse* secret than the one you're protecting. Circular.
3. **Post-deploy push over SSH (chosen).** `scripts/bootstrap-secret.sh` reads the secret
   with your own (SSO) credentials, then pipes it over SSH stdin into a `0600` root file.
   SSH uses **Lightsail's short-lived certificate** from `GetInstanceAccessDetails`, so no
   key pair is downloaded or stored, and the host keys from the same call give strict host checking.
   The secret never touches CFN, user data, IMDS, argv or git. Rotation means re-running the script.
- A systemd `.path` unit watches for the secret file, so "drop the file" is the whole
  interface. Bootstrap stays automatic and survives reboots.

### The user-data replacement trap
- `AWS::Lightsail::Instance.UserData` changes force **replacement**. Bumping an image tag
  in the repo and running `cdk deploy` would hand you a brand-new, empty box.
- Mitigation: synth fingerprints the rendered user data (tokens masked) and outputs it.
  Pin it in `config.local.json`, and synth then **fails** if a change would replace the
  instance, unless you pass `-c replaceInstance=true`. Day-2 upgrades go through
  `scripts/upgrade.sh`, which snapshots, edits compose on the box and pulls.

### Static IP vs. user data cycle
- Headscale's embedded DERP wants `derp.server.ipv4` = the public IP. The static IP
  attaches *to* the instance, so its address can't be baked into the instance's own
  user data without a cycle. The template ships `__PUBLIC_IPV4__`, and the bootstrap
  script fills it in from the stack output (with an IMDS fallback).

### Secrets inventory: where everything lives
| Secret | Generated by | Lives at | Never in |
|---|---|---|---|
| Cognito client secret | Cognito | `/opt/headscale/secrets/oidc_client_secret` (0600) | CFN, user data, git |
| Headplane cookie secret | `openssl rand -hex 16` on first boot | `.../headplane_cookie_secret` | anywhere off-box |
| Headscale API key (for Headplane) | `headscale apikeys create --expiration 999d` | `.../headscale_api_key` | anywhere off-box |

Headplane reads all three via `*_path` keys (it trims whitespace), so its config file
holds no secrets.

### Cognito specifics
- **One** confidential client for both Headscale and Headplane, so the OIDC `sub` is
  identical and Headplane links your login to your Headscale user automatically.
- Cognito's userinfo endpoint has historically returned `email_verified` as the
  *string* `"true"`. Headscale 0.29 parses it with a `FlexibleBoolean` type (added for
  JumpCloud), so this works.
- Headscale `allowed_users` matches on email, and only trusts **verified** emails
  (`email_verified_required: true`). Admin-created users must be created with
  `email_verified=true`, or Headscale rejects you with no obvious reason.
- Users signing in by email have no `preferred_username`, so Headscale falls back to
  the email as the username.
- Managed login v2 (the new UI) needs the **Essentials** feature plan, plus a
  `ManagedLoginBranding` resource for the client, or the hosted page errors. Essentials is free under 10k MAU.
- `token_endpoint_auth_method`: Cognito's discovery doc advertises both
  `client_secret_basic` and `client_secret_post`. Pinned to basic.

### Caddy
- One hostname: `/admin*` goes to Headplane (which serves itself under `/admin`, so no
  prefix stripping), everything else to Headscale. Caddy passes the `/ts2021` Noise
  upgrade and the `/derp` upgrade through with no special config. That's different from
  nginx, where you need the `Upgrade`/`Connection` header incantation.
- HTTP/3 disabled (`protocols h1 h2`) because UDP 443 isn't open; otherwise Caddy
  advertises `alt-svc: h3` for a port that's firewalled.
- `trusted_proxies` (new in Headscale 0.29) is set to the fixed compose subnet, so logs
  show real client IPs.

## Cost (us-east-1, Nov 2026)
- Lightsail `micro_3_0` (1 GB / 40 GB / 2 TB transfer, **IPv4 included**): **$7.00**
  - `nano_3_0` (512 MB) is $5 and might work with swap; `*_ipv6` bundles are $2 cheaper
    but IPv6-only, which breaks IPv4-only clients.
- Static IP: free while attached.
- Auto snapshots: ~$0.05/GB-month of snapshot storage, so roughly $0.25-1.00.
- Route 53: hosted zone already existed ($0.50, shared); queries are pennies.
- Cognito Essentials: $0 under 10k MAU.
- **Total: about $7.50-8/month.**

## Deploy log (2026-11-22, first real deploy)

1. **First deploy: 158 s.** Cognito pieces took seconds; the Lightsail instance took most of the time.
   `Networking.Ports` in CFN really does *replace* Lightsail's default firewall: 22 was
   open only to my IP plus `lightsail-connect`, and 80/443/3478 were open. No IPv6 rules, as intended.
2. **Gotcha #1: Lightsail ignores your shebang.** cloud-init failed with
   `set: Illegal option -o pipefail`. Lightsail *prepends* its own launch script (it sets
   up the SSH CA for browser/cert SSH) and runs the whole thing with `/bin/sh` (dash on
   Ubuntu). Fix: a POSIX outer wrapper that writes the real bash script to disk and runs
   `bash` on it. A test now asserts the outer part stays POSIX.
   - Side note: Lightsail's own script logs `Failed to restart sshd.service: Unit sshd.service
     not found` on 24.04 (the unit is `ssh.service`), then says "sshd restarted". Cert SSH
     still worked, so it's harmless.
3. **Gotcha #2: instance replacement needs a new name.** CFN creates the replacement
   *before* deleting the old instance, and Lightsail names are unique, so a fixed
   `instanceName` would fail. The name now carries the user-data fingerprint
   (`headscale-f1808a0e`). Replacement then just works: the **static IP moved to the new
   instance by itself** (CFN updated `AttachedTo`), and DNS never changed. Each replace took ~105 s.
4. **Gotcha #3: Headplane 0.8.2 rejects its own example config.** The example ships
   `integration.kubernetes: { enabled: false, ... }`. If you trim it to just
   `enabled: false`, validation fails with `integration.kubernetes.pod_name must be a string`
   and the container crash-loops. Fix: omit the kubernetes/proc blocks entirely.
   - Debug method: hot-fix on the box over SSH, verify, *then* fold the fix into the template,
     because every template change is an instance replacement.
5. **Gotcha #4: Let's Encrypt duplicate-certificate limit.** Each replacement throws away
   Caddy's `/data` volume, so it requests a new cert. 3 replacements = 3 certs for
   `hs.martzmakes.com` in an hour; the limit is 5 per week. Worth an EBS-style persistent
   disk? Not for $0.80/month. Just don't churn the instance.
6. **Verification that worked without a real user:**
   - `curl /health` 200, `/key?v=120` returns the Noise public key, `/derp/probe` 200, HTTP→HTTPS 301, `/` → `/admin/`.
   - Headplane SSO: `/admin/login` → `/admin/oidc/start` → Cognito `/oauth2/authorize` with
     `redirect_uri=/admin/oidc/callback`, PKCE `S256`, and Cognito forwards to its `/login` page (no `redirect_mismatch`).
   - Headscale OIDC: a throwaway **userspace** `tailscaled` on the Mac (no root:
     `tailscaled --tun=userspace-networking --socket=... --statedir=...`) ran
     `tailscale login --login-server ...`. That proves `/ts2021` Noise works through Caddy,
     because you only get a `/register/hskey-authreq-...` URL after the control handshake.
     That URL 302s to Cognito with `redirect_uri=/oidc/callback` and PKCE S256.
   - Probing `/ts2021` with plain curl gives a 500 plus "no upgrade header". curl negotiated
     HTTP/2, which can't Upgrade. Real clients use HTTP/1.1, so it's a red herring.
7. **Memory:** 525 MB used out of 909 MB with all three containers up (plus 1 GB swap). The 1 GB bundle is fine.
8. **MFA:** `mfa: OPTIONAL` + TOTP means managed login *never* offers TOTP enrollment.
   Switching the pool to `ON` (required) is an in-place CFN update (16 s) on an existing pool,
   and the next sign-in shows the QR setup, which goes straight into 1Password.

## Onboarding the home network (2026-11-22, same afternoon)

- **First real login worked**. Matt signed in through Cognito from the iPhone, and Headscale created user 1
  (my email, used as the username, since Cognito has no `preferred_username`). The iPhone
  registers as hostname `localhost`; its Tailscale device name shows as `duo`.
- **TerraMaster NAS (TOS 3.x, kernel 4.19, Docker 17.05 from 2017)**:
  - `docker pull` fails with `x509: certificate signed by unknown authority` against `auth.docker.io`.
    The appliance's CA bundle is ancient. Fix: `tools/fetch-image.py` pulls the amd64 manifest +
    layers from the registry API on the Mac, writes a `docker save`-format tar (compressed layers are fine;
    `docker load` detects gzip), and pipes it over SSH into `docker load`. Docker 17.05 ran the
    2026 tailscale image without complaint.
  - Compose file `version: "2.2"`. 2.3+ needs Engine 17.06.
  - `network_mode: host`, `/dev/net/tun`, `NET_ADMIN`. Came up in seconds, chose the **embedded DERP**
    (`derp-999`, 7 ms) as home, firewall mode `ipt-default`. Harmless warning: `src_valid_mark`
    sysctl is read-only inside the container.
  - IPv4 forwarding was already on and IPv6 off, so the exit node is effectively IPv4-only. `tailscale status`
    prints "IP forwarding is disabled" because of the v6 half.
  - Routes approved with `headscale nodes approve-routes -i 2 -r 192.168.68.0/22,0.0.0.0/0,::/0`.
- **Pi-hole v6 for tailnet clients**: the box was deliberately hardened (`listeningMode: LOCAL`, plus
  `listen-address=127.0.0.1,<LAN>;bind-interfaces`). LOCAL silently drops 100.x sources. Instead of
  "Permit all origins", I used `listeningMode: NONE` and added the tailnet IP to `listen-address`, with
  `bind-dynamic` so a missing `tailscale0` at boot can't take down LAN DNS. DNS outage during recreate: ~3 s.
- **Proving remote DNS without a phone**: userspace tailscaled has no TUN, so `dig @100.64.0.2` won't
  route. Instead: DNS-over-TCP through `tailscale nc 100.64.0.2 53` (a 30-line Python query builder).
  Gotcha: `tailscale nc` closes as soon as stdin hits EOF, so keep stdin open until the reply arrives.
  Result: `doubleclick.net -> 0.0.0.0`, `example.com -> real IPs`, sourced from the mini's 100.64.0.4.
- **The Mac mini without sudo**: brew's `tailscaled` in userspace mode as a LaunchAgent. It joined in one
  command with a pre-auth key and reached the NAS directly over the LAN (5 ms, no DERP).

## Hardening after onboarding (2026-11-22, evening)

- **Policy:** kept allow-all (one-person tailnet; the work laptop being able to reach things is fine
  by me) but added `autoApprovers` for the LAN route + exit node and an `ssh` rule for
  `autogroup:self`. `headscale policy check -f` validates before `policy set`. OIDC users are referenced by email.
- **Health alarm:** Route 53 HTTPS health check on `/health` (30 s, 3 failures) -> CloudWatch alarm
  (`HealthCheckStatus` Minimum < 1 for 3 min, missing data = breaching) -> SNS email, alarm *and* OK
  actions. ~$0.60/mo. 16/16 checkers green on first look. In-place deploy, no instance change.
  Why it matters: a dead control plane is silent, since existing WireGuard tunnels keep working.

## Backup Pi-hole on the Lightsail box (2026-11-22, late)

- **Why:** with `override_local_dns: true` and one home Pi-hole, a home power or ISP outage
  means my phone in Vegas has *no DNS at all* until I notice and toggle Tailscale off.
- **How (in place, no replacement):** the box joins its own tailnet as `cloud-dns` (100.64.0.6) via a
  host-network `tailscale` container. A `pihole/pihole:2026.10.1` container (the same Core 6.5 / FTL 6.8 as
  the NAS) binds only `127.0.0.1` and `100.64.0.6` (`listeningMode: NONE` + `listen-address` +
  `bind-dynamic`). systemd-resolved keeps 127.0.0.53/54, so there's no port-53 fight. UDP 53 is not in the
  Lightsail firewall, and `dig @<static IP>` from the internet times out.
- **Same lists:** I streamed a Teleporter export NAS → mini → box over SSH pipes (never written to the
  mini's disk), ran `pihole-FTL --teleporter <zip>`, then `pihole -g`: 453,084 unique domains. The FTLCONF_
  environment variables win over imported `pihole.toml` values, so the import couldn't widen listening.
- **Memory:** ~510 MB used of 909 MB with five containers. It still fits the $7 bundle.
- **Failover drill:** testing "is the backup used?" needs a client that accepts tailnet DNS. Doing that on
  the mini risked breaking its system DNS, so I ran a throwaway **ephemeral userspace client in a container on the
  box** (`TS_ACCEPT_DNS=true`, `TS_STATE_DIR=mem:`). Baseline answers came through the normal path. Then I
  stopped Tailscale on the NAS: `doubleclick.net -> 0.0.0.0`, `example.com` and `github.com` resolved, each in ~92 ms.
  The NAS was back after 11 s.
- **Gotcha:** after the NAS restarted it came back on a new random UDP port. The iPhone, Air and work
  laptop re-established direct paths immediately, but the mini (userspace) kept the stale endpoint for
  ~2 minutes until the NAS pinged it.
